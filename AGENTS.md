# AGENTS.md

Guidance for any coding agent (or human) contributing to ClaudeTerm. `CLAUDE.md` in this repository points here
so Claude Code picks up the same rules. [CONTRIBUTING.md](CONTRIBUTING.md) has the setup steps for people; this
file is the rulebook every change is held to.

## Project

ClaudeTerm is a terminal built for Claude Code, on Windows 10/11 and Linux: Electron 44, TypeScript, xterm.js and
node-pty (ConPTY on Windows). It runs shell tabs and Claude tabs, and gives Claude tabs an image panel, a Changes
(code review) panel, a status bar and session restore. It learns what Claude does only from Claude Code's own
hooks, `statusLine` and transcript files — it never patches Claude Code.

| Folder | What it is |
|---|---|
| `src/main` | Electron main process: tabs and PTYs, settings, shell profiles, the named-pipe server, transcripts, the image panel's and the Changes panel's sources (git, the edit ledger), the status bar state |
| `src/renderer` | The UI in plain TypeScript, no framework: terminals, tab bar, side panels, lightbox, status bar, settings window |
| `src/preload` | The `window.ct` bridge, the renderer's only way to the system |
| `src/shared` | Types, IPC channel names and the pipe protocol shared by all parts |
| `src/hook` | The script Claude Code runs for its hooks and `statusLine`; reports to the app over the pipe |
| `src/mcp` | The bundled `claudeterm` MCP server: `show_image`, `show_diff` |
| `tests` | `unit/`, `integration/`, `e2e/`, `screenshots/`, `fixtures/` |
| `build/`, `scripts/` | Installer resources; build and release helper scripts |
| `docs/` | README images and the design notes and plans in `docs/superpowers` |

`resources/hook/*.js` and `resources/mcp/*.js` are generated by `npm run build` and are not committed.

## Build and test

```
npm ci
npm run typecheck     # the app, the tests and the configs
npm test              # unit and integration tests (Vitest)
npm run test:e2e      # builds, then end-to-end tests against the real Electron app (Playwright)
npm run screenshots   # regenerates the README images
```

CI runs typecheck, `npm test`, the build and the e2e suite on **both `windows-latest` and `ubuntu-latest`**, and
a change is done only when both are green. On Linux without a display the e2e tests run under `xvfb-run -a`, with
`ELECTRON_DISABLE_SANDBOX=1` where there is no setuid sandbox helper (Ubuntu 24.04, WSL).

## Bug fixes need a proving test

A bug fix is accepted only together with a test that proves it: the test reproduces the bug, fails on the code
before the fix and passes after it. The pull request names the test and shows the failure before the fix (the
test run output, or the exact steps). A fix without such a test is not accepted.

## New features need tests

A new feature or any change of behavior is accepted only together with tests that cover it: every behavior the
pull request adds or changes has a test that exercises it through the entry point that uses it (a pipe message, a
hook run, an IPC call, a click in the window), and that test fails when the feature is removed or broken. Tests
assert behavior, not implementation details. Write the test first and watch it fail. A feature without such tests
is not accepted, however small it is.

| Level | What goes there | Lives in | Run |
|---|---|---|---|
| Unit | Pure logic: parsers, formatting, state machines, the hubs with fake dependencies | `tests/unit/*.test.ts` | `npm test` |
| Integration | Anything that crosses a process or disk boundary: the pipe, the hook script, transcripts on disk, real `git` in a temp repository | `tests/integration/*.test.ts` | `npm test` |
| End-to-end | What a person sees and does in the window | `tests/e2e/*.spec.ts` | `npm run test:e2e` |

Tests never touch the machine they run on: e2e tests start the app with its own data folder, pipe name and a
stand-in `claude` command (`tests/e2e/helpers.ts`), and anything Claude would write goes to a temp folder with
its own `CLAUDE_CONFIG_DIR`. No test may start the real `claude`, call the Anthropic API, register the MCP server
for the real user, or read or write the real `~/.claude` or `%APPDATA%\ClaudeTerm`.

## Code rules

- **Match the surrounding code**: its naming, comment density and idioms. TypeScript is strict
  (`noUnusedLocals` too) and the tests are type-checked. No UI framework in the renderer.
- **Comments, logs and every UI-visible string are English.**
- **The hook script never prints to stdout** (Claude Code puts `SessionStart` output into the conversation and
  shows `statusLine` output in its UI), always exits with code 0, quickly, even when ClaudeTerm is not running.
- **Everything from the pipe and from transcript files is untrusted.** Any local process can write to the pipe,
  and transcript formats change between Claude Code versions: validate, and degrade gracefully.
- **The renderer stays sandboxed**: it reaches the system only through the preload bridge, and images only
  through the `ctimg://` protocol. Main checks every IPC argument (`ipc-guards.ts`).
- **Paths are compared with `pathKey`** (case-insensitive on Windows), never as raw strings. Expect `/` and `\`,
  short 8.3 names (`C:\Users\RUNNER~1` on the CI runner), junctions and symlinks: test path code with them.
- **Git runs only through `execGit`** (`src/main/git-source.ts`): no shell, `--no-optional-locks`, no fsmonitor,
  literal pathspecs. ClaudeTerm only reads the user's repository — it never writes to it or takes its index lock.
- **The main process must not block**: long work yields to the event loop or has a time limit, so the pipe and
  the window stay responsive in a large repository.
- **Keep a file's existing line endings.**

## Not allowed

- No secrets (API keys, tokens) in code, history, logs or fixtures.
- No real personal data in tests, fixtures, screenshots or the README: invented projects, paths, names and
  sessions only.
- No commits of generated files (`out/`, `dist/`, `resources/hook/*.js`, `resources/mcp/*.js`).

## Pull requests

- Keep a PR to one change; say what it fixes or adds and why, not just what changed.
- Show the checks you ran — `npm run typecheck`, `npm test`, `npm run test:e2e` — and their result. For a bug
  fix, follow "Bug fixes need a proving test"; for a feature or behavior change, "New features need tests". A
  pull request without the tests these sections require is closed, not merged.
- If the change affects what the README shows, run `npm run screenshots` and commit only the images that changed
  because of it.
- Commit messages follow [Conventional Commits](https://www.conventionalcommits.org): `feat: …`, `fix: …`,
  `docs: …`, `test: …`, `chore: …`.
- By opening a pull request you agree your contribution is licensed under the [MIT License](LICENSE).

## Releases (maintainers)

- A release's notes are its section in [CHANGELOG.md](CHANGELOG.md), written by hand for the people using the app
  (New / Changes / Fixes) — never a list of commits. The Release workflow stops when the section is missing.
- Versions: a release with a new feature bumps the middle number (`0.1.9` → `0.2.0`); fixes and small updates bump
  the last one (`0.2.0` → `0.2.1`).
- Push a tag `vX.Y.Z` matching `package.json` once CI is green on both systems; the Release workflow builds the
  Windows installer and the Linux package and publishes the GitHub release.
