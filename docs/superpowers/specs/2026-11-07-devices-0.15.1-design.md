# Devices 0.15.1: follow-ups to device sync

The ten follow-ups that 0.15.0's whole-branch review and its fix rounds left open (see the 0.15.0 decision list), and
one older bug that CI on the 0.15.0 release found (section 11). The user asked for the ten to be taken into work ("это
бери в работу") and, as before, for every open question to be decided by Claude ("сам решай"). Every decision below
that the user did not state is marked *(Claude's call)*.

0.15.1 is a fix release: the third number goes up. Specs: `2026-11-04-device-sync-design.md` and
`2026-11-04-remote-tabs-design.md` still hold; this note changes them only where it says so.

## 1. Presence: the device the person is at decides who rings

**The problem.** In 0.15.0, a tab's attention (a turn end, a question, a permission prompt) is one shared state that
every device signals under its own rules. When the person watches the tab in front on A, A stays quiet, but B rings,
flashes, pops a system notification and pulses the tab, until the next prompt. And the other way round, when they
watch A's tab on B. Window focus alone cannot settle it: both windows can be focused at once, and a window keeps its
focus when the person turns to the other machine.

**The rule.** A device is *present* when its ClaudeTerm window is focused and the machine has had keyboard or mouse
input within the last 30 seconds. *(Claude's call: Electron's `powerMonitor.getSystemIdleTime()` gives the seconds
since the last input on the whole machine; 30 s.)*
- An attention starts on no device when the tab is in front on a present device. That device counts the tab as seen,
  and the other devices are not told.
- A case set to *Even in front* still sounds on the present device, as it does today, and starts nowhere else.
- When no device is present (the person walked away, or reads without touching anything for 30 s), everything works
  as in 0.15.0: the attention starts and every device signals under its own rules. A missed signal is worse than an
  extra one.
- A device that becomes present with the tab in front clears the tab's attention everywhere, as bringing the tab to
  the front does today.

**How it travels.**
- The member's `front` message already has an optional `focused`. It gains an optional `present: boolean`. Absent
  means not present, so an older peer keeps 0.15.0 behavior. `focused` is still sent, with the value of `present`, so
  a 0.15.0 host keeps clearing a tab that an updated device brings to the front.
- Locking the screen or sleeping makes the device not present at once; unlocking or waking reads it again.
- A device sends `front` again when its presence changes. It reads its idle time every 5 seconds while its window is
  focused, and not otherwise. *(Claude's call: also while a tab of its own is in front, since the device that becomes
  present must clear its own tab's mark too; one idle-time read per 5 s costs nothing.)*
- The tab's own device reads its own presence the same way when an attention would start.
- When the present device is another device, the tab's device sends it a new `ring` message (`{ t: 'ring', id,
  reason }`), and that device runs its own rules for a tab in front of a focused window: only a case set to *Even in
  front* sounds. *(Claude's call: a new message, because the attention itself is not shared in this case; an older
  peer drops a message type it does not know.)*
- The same check covers every place an attention starts: the hook's attention, a bell, and the auto-continue that gave
  up.

**Not changed.** This device's own signals for its own tabs follow master's rules, which count a focused window with
the tab active as seen, idle or not.

## 2. ⟳ always says when the device is offline

**The problem.** On a tab of a device that went offline, opening Changes refreshes in the background, and an offline
device is not asked, so nothing is toasted. That part is right. But the ⟳ button does nothing while the panel has no
review for the tab: a device that went offline before its first review push reached this device leaves the click
silent, so the person gets no "Studio is not connected". `remote-tabs.spec.ts:426` flakes on this when the device is
closed before its review arrives. *(The research found no joining of refreshes; this replaces the first guess.)*

**The rule.** A person's ⟳ click on a tab of an offline device always toasts `REMOTE_COPY.deviceOffline(name)`, once,
whatever refresh is running.

## 3. Paths typed into another device's tab are quoted for that tab's shell

**The problem.** A path pasted or dropped into a tab of another device is typed in fixed double quotes. The folder part
is the receiving device's own temp folder, and a `$`, `!`, `%` or backtick in it would expand in bash, PowerShell or
cmd.

**The rule.** The receiving device builds the text to type, because only it knows the tab's shell:
- `quoteForShell(shellFamily(profile), path)` for a shell tab;
- `"…"` for a Claude tab, as for a local Claude tab.

The `recv-end` answer carries that text, bounded like the paths it already carries, and the sending device types it
unchanged. A local drop already quotes for the local shell; check it, and fix it the same way if it does not.

## 4. The image-paste keys work in another device's Claude tab

**The problem.** On macOS, Ctrl+V typed straight into another device's Claude tab reaches that device as `\x16`, so
Claude Code there reads that device's clipboard, not this one. Alt+V does the same on Windows.

**The rule.** In another device's Claude tab, Claude Code's image-paste key goes through the same route as
ClaudeTerm's own paste key: Ctrl+V on macOS, Alt+V on Windows. On Linux Ctrl+V is already ClaudeTerm's own smart
paste, which takes that route. Find the exact keys in Claude Code's behavior as `keymap.ts` and `imagePasteRoute`
already model it.
- When this device's clipboard holds an image, the image is copied to the tab's device and its path is typed there.
- With no image, the key goes through unchanged.

## 5. An open Changes panel comes back after a network drop

**The problem.** After a reconnect with the same tab ids, an open Changes panel of a device's tab may stay stale until
⟳.

**The rule.** When a device's link comes back, an open Changes panel of one of its tabs shows that device's latest
review without a ⟳. *(Claude's call: prove it first. The code suggests the re-attach already brings the latest review;
if a test of a drop and a return passes on today's code, the item is closed by that test, and no code changes.)*

## 6. A session listed by two devices opens where it was picked

**The problem.** When two online devices list the same session id (the same transcript on both), Recent sessions shows
it in both sections, but a pick opens it on whichever device's answer was kept first.

**The rule.** A pick carries the device of the section it was made in, and opens there. This device's own section
keeps the session local.

## 7. A turn answered at once leaves no mark behind

**The problem.** Remote attention for `done` starts after the transcript poll. If the person types or brings the tab
to the front during those milliseconds, the clear runs first and does nothing, and the attention that follows stays on
the other devices until the next prompt.

**The rule.** Each tab has an input counter. Every prompt input, every activation of the tab and every front that
clears its mark bump it. `signal()` captures the counter when the attention message arrives, and starts nothing, here
or anywhere, if the counter has moved by the time the poll answers. *(Claude's call: a front that would not clear the
mark, such as a window that loses the person, does not count as an answer.)*

## 8. A large Changes push does not hold up the window

**The problem.** A review push near the 12 MiB cap is clamped synchronously on the tab's device, and parsed with one
`JSON.parse` of up to 16 MiB on the other.

**Measured** (research, a fast desktop; CI runners are 2–3× slower): clamp and encode on the tab's device take 50–80
ms in one task, parse and check on the other 27–48 ms, for reviews of 8–12 MiB. So the yield-and-split branch below
applies.

**The rule.** Measure first, with a fixture near the cap, on the CI-sized machine.
- If either side takes more than 50 ms of one main-thread task, make it yield: clamp per file with a yield between
  files, and split the push so that no single message carries more than 2 MiB of review text. *(Claude's call: the
  numbers.)*
- If neither side takes that long, keep the code and add the measurement as a test that fails above the limit.

## 9. The received folder works on shared and on Unicode-normalizing file systems

- **Linux.** On a machine where `/tmp` is shared, the received folder's parent is per user: `ClaudeTerm-<uid>` on
  POSIX. Windows keeps `ClaudeTerm`, because its temp folder is per user already.
- **macOS.** Names are compared in NFC, so two dropped names that differ only in Unicode normalization get distinct
  names (the usual ` (2)` suffix) instead of a `receiveFailed`.

## 10. A tab that exits while it waits, and a slow quit on Windows

- **Exit.** A tab whose process exits on its own while it waits for the person clears its attention on every device.
  That code exists; it needs its test.
- **Quit.** On Windows under load, quitting can stall in `disposeAll`, which waits for each ConPTY kill in turn.
  Measure first.
  - If the kills are waited for one after another, start them all at once and wait for all, with the time limit that
    exists today.
  - If the stall is ConPTY's own, leave the code and document the case.
  - **Measured** (10 PowerShell ConPTY tabs, this machine): the kills take 129 ms in all, the slowest 15 ms, and every
    process is gone after 198 ms. Under 16 busy loops the figures are 151 ms, 16 ms and 217 ms. The waits already run at
    once (`allPtysExited`), and nothing stalls, so the code stays as it is. The slow quits seen before were the e2e
    machine's, not the app's.

## 11. A click on a tab is not lost when the tab bar redraws

Not on the 0.15.0 list: CI on the 0.15.0 release commit found it (`accounts.spec.ts:190` on Windows), and it is older
than devices.

**The problem.** The tab bar and the tab panel on the left build every tab's element again on each redraw, and a busy
Claude retitles its tab every second. A click whose press lands on the old element and whose release lands on the new
one fires no `click`, so the tab is not activated. On the CI runner, a PowerShell tab's title gains `Administrator: `
just when the test clicks.

**The rule.** A press and a release on the same tab activate it, even when the tab's element was built again between
the two, in the tab bar and in the panel alike. A press on one tab that is released on another activates neither, as
today. *(Claude's call: the fix tracks the pressed tab's id, not the element; keeping the elements across redraws would
touch more code for the same result.)*
