# Devices 0.15.1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Fix the eleven follow-ups of device sync listed in the spec, each with a test that fails before the fix.

**Architecture:** Each task is one spec section, fixed where the research found its cause. Presence (sections 1 and 7)
lives in a new `src/main/sync/presence.ts`, the `front` and new `ring` peer messages, and one attention-raising helper
in `src/main/index.ts`. A large review travels in parts of at most 2 MiB (section 8). The rest are local fixes in the
renderer, the file receiver and the remote calls.

**Tech Stack:** Electron 44, TypeScript (strict), node-pty, Vitest (unit, integration), Playwright (e2e).

**Spec:** `docs/superpowers/specs/2026-11-07-devices-0.15.1-design.md`. The research behind the file and line
references is in `.superpowers/sdd/2026-11-07-devices-0.15.1/research-*.md` (git-ignored).

**Files:**

  `tests/integration/sync-remote-tabs.int.test.ts`

**Interfaces:**
- Produces, in `src/shared/remote.ts`:
  - `REVIEW_PART_BYTES = 2 * 1024 * 1024`;
  - `REVIEW_FILE_BYTES = REVIEW_PART_BYTES - 64 * 1024`;
  - `MAX_REVIEW_PARTS = 16`;
  - `PushKind` gains `'review-part'`.
- Produces, in `src/main/remote-host.ts`: `export async function reviewPushes(v: unknown, rev: number, o: { yieldNow():
  Promise<void>; stale(): boolean }): Promise<{ k: 'review' | 'review-part'; v: unknown }[] | null>`.
  - It clamps the files one by one with `await o.yieldNow()` between files, and returns `null` as soon as `o.stale()`.
  - When the clamped review's JSON is at most `REVIEW_PART_BYTES`, it returns one `{ k: 'review', v: { ...clamped,
    rev } }`.
  - Otherwise it returns parts `{ k: 'review-part', v: { rev, i, of, head?, files } }`. `head` is in part 0 only and is
    the clamped review without `files`. Each part's JSON is at most `REVIEW_PART_BYTES`, and its files keep their
    order.
- The same per-file rule in `clampFiles` (used by `clampPush`): a file whose encoded size is over `REVIEW_FILE_BYTES`
  keeps its header with `hunks: []` and `note: 'too-many'`, as a file past the cap does today. *(Ruling: one huge file
  is not shown line by line on another device; locally it still is.)*
- The viewer keeps, per tab, the highest `rev` it has shown. A `review` or a part whose `rev` is lower is dropped. A
  `review` with no `rev` comes from an older device and is shown as today. Part 0 of a higher `rev` starts an
  assembly. A part that is not the next one of the current assembly drops the assembly. After the last part, the viewer
  emits one ordinary `review` push event with `{ ...head, files }`. The total of files stays within `MAX_REVIEW_FILES`.
  The assembly is dropped when the tab closes or the link drops.

- [ ] **Step 1: Write the failing tests**
  - Unit `reviewPushes`:
    - A review with 40 files of 512 lines of 1 KiB (the fixture of the test at ~470) gives parts each under
      `REVIEW_PART_BYTES` of JSON. Their files concatenated equal `clampPush('review', v).files`, and `yieldNow` was
      awaited at least once per file.
    - A small review gives one `review` push carrying `rev`.
    - `stale()` turning true mid-way gives `null`.
    - A file over `REVIEW_FILE_BYTES` comes out as a header with `note: 'too-many'`.
  - Unit shapes: the part validator accepts a good part. It refuses `i >= of`, `of > MAX_REVIEW_PARTS`, a part 0
    without `head`, a part > 0 with `head`, and a non-integer `rev`.
  - Integration, with a host and a viewer over a real link:
    - Parts of rev 2 arrive and the viewer emits one review equal to the assembled clamp.
    - Rev 3's parts interleaved after rev 2's part 0 end on rev 3.
    - A `review` of rev 1 arriving after rev 2's assembly is dropped.
    - No `push` message on the wire is over `REVIEW_PART_BYTES`: wrap the link's `sendBulk` and measure each message's
      JSON.
- [ ] **Step 2: Run; they fail.**
